We only merge the two when the diff is complete because it ensures we don\u0026#8217;t accidentally return a partial result for a query that doesn\u0026#8217;t tolerate partial results (e.g. when \u003ccode class=\"\" data-line=\"\"\u003ereturnPartialData\u003c/code\u003e is \u003ccode class=\"\" data-line=\"\"\u003efalse\u003c/code\u003e). \u003c/p\u003e\n\n\n\n\u003cp class=\"wp-block-paragraph\"\u003eThe problem is that the \u003ccode class=\"\" data-line=\"\"\u003ediff\u003c/code\u003e held the needed parsed scalar values but in-flight \u003ccode class=\"\" data-line=\"\"\u003e@defer\u003c/code\u003e queries are partial by nature so these values were not applied to the end result. For those of you that use field policy \u003ccode class=\"\" data-line=\"\"\u003eread\u003c/code\u003e functions and happened to notice a similar issue where intermediate incremental results didn\u0026#8217;t return the values returned by those functions, this is your root cause. So we needed to seek out a solution that solved both issues at once.\u003c/p\u003e\n\n\n\n\u003cp class=\"wp-block-paragraph\"\u003eWe determined that what we needed was a \u003ccode class=\"\" data-line=\"\"\u003e@defer\u003c/code\u003e-aware cache read so that we could safely apply values from the cache to the network result, even if some \u003ccode class=\"\" data-line=\"\"\u003e@defer\u003c/code\u003e fragments hadn\u0026#8217;t been delivered by the network, to ensure we were returning parsed custom scalar and \u003ccode class=\"\" data-line=\"\"\u003eread\u003c/code\u003e function values. What made this especially difficult is the need to maintain backwards compatibility with existing cache reads (i.e. we can\u0026#8217;t just return a defer-aware result all-of-a-sudden when you don\u0026#8217;t expect it) and handle distinguishing between partial data inside \u003ccode class=\"\" data-line=\"\"\u003e@defer\u003c/code\u003e boundaries vs non-deferred or non-streamed fields. After all, the reason the cache result wasn\u0026#8217;t applied to begin with was to avoid returning partial data where it wasn\u0026#8217;t expected.\u003c/p\u003e\n\n\n\n\u003cp class=\"wp-block-paragraph\"\u003eThis led to the introduction of data pruning during cache reads: the ability to strip away data at \u003ccode class=\"\" data-line=\"\"\u003e@defer\u003c/code\u003e boundaries or \u003ccode class=\"\" data-line=\"\"\u003e@stream\u003c/code\u003e arrays in order to satisfy the data needs for the query while maintaining completeness guarantees. The approach first performed a cache read for all fields in the query to assemble the object while noting the location of defer boundaries and the completeness at those locations. A 2nd pass is then performed over the data to prune any data at incremental boundaries marked as partial. If you\u0026#8217;re curious how this came together, see \u003ca href=\"https://github.com/apollographql/apollo-client/pull/13347\"\u003e#13347\u003c/a\u003e which focused on the changes to make this work.\u003c/p\u003e\n\n\n\n\u003cp class=\"wp-block-paragraph\"\u003eThis worked great! We could now apply query value transformed by the cache to the end result without leading partial data into the end result. But this led to the discovery of another data consistency issue. To illustrate, let\u0026#8217;s use the following query as an example:\u003c/p\u003e\n\n\n\n\u003cpre class=\"wp-block-prismatic-blocks\"\u003e\u003ccode class=\"language-typescript\" data-line=\"\"\u003equery {\n user {\n id\n name\n ... @defer {\n email\n }\n }\n}\u003c/code\u003e\u003c/pre\u003e\n\n\n\n\u003cp class=\"wp-block-paragraph\"\u003eAnd a cache that looks like the following:\u003c/p\u003e\n\n\n\n\u003cpre class=\"wp-block-prismatic-blocks\"\u003e\u003ccode class=\"language-typescript\" data-line=\"\"\u003e{\n ROOT_QUERY: {\n user: \u0026quot;User:1\u0026quot;,\n },\n \u0026quot;User:1\u0026quot;: {\n \u0026quot;id\u0026quot;: \u0026quot;1\u0026quot;,\n \u0026quot;email\u0026quot;: \u0026quot;user@example.com\u0026quot;,\n }\n}\u003c/code\u003e\u003c/pre\u003e\n\n\n\n\u003cp class=\"wp-block-paragraph\"\u003eNote how the cache data contains a value for \u003ccode class=\"\" data-line=\"\"\u003eemail\u003c/code\u003e (which is the deferred field), but not \u003ccode class=\"\" data-line=\"\"\u003ename\u003c/code\u003e. Executing this query with a \u003ccode class=\"\" data-line=\"\"\u003ecache-first\u003c/code\u003e or \u003ccode class=\"\" data-line=\"\"\u003ecache-and-network\u003c/code\u003e fetch policy correctly returns \u003ccode class=\"\" data-line=\"\"\u003edata\u003c/code\u003e as \u003ccode class=\"\" data-line=\"\"\u003eundefined\u003c/code\u003e for the first value because the result is partial:\u003c/p\u003e\n\n\n\n\u003cpre class=\"wp-block-prismatic-blocks\"\u003e\u003ccode class=\"language-typescript\" data-line=\"\"\u003econst result = useQuery(QUERY)\n// =\u0026gt; { data: undefined, dataState: \u0026quot;empty\u0026quot;, loading: true, ... }\u003c/code\u003e\u003c/pre\u003e\n\n\n\n\u003cp class=\"wp-block-paragraph\"\u003eBut something interesting happens when the first chunk arrives from the server. The server emits the first chunk which contains the \u003ccode class=\"\" data-line=\"\"\u003ename\u003c/code\u003e, but not the \u003ccode class=\"\" data-line=\"\"\u003eemail\u003c/code\u003e. Once \u003ccode class=\"\" data-line=\"\"\u003ename\u003c/code\u003e is written to the cache, the cache can now fulfill the entirety of the query, but should it actually return \u003ccode class=\"\" data-line=\"\"\u003eemail\u003c/code\u003e even though the network hadn\u0026#8217;t delivered it yet? Should the result strip away the \u003ccode class=\"\" data-line=\"\"\u003eemail\u003c/code\u003e since it was never delivered? Or should it keep the possibly stale cache value? Had \u003ccode class=\"\" data-line=\"\"\u003eemail\u003c/code\u003e not been written to the cache, this same query would have returned a final result without \u003ccode class=\"\" data-line=\"\"\u003eemail\u003c/code\u003e. A cache feud is when two or more queries compete over an overlapping field\u0026#8217;s data such that fetching and writing data from one query causes another query to be incomplete and refetch and vice versa. Cache feud detection, introduced as far back as \u003ca href=\"https://github.com/apollographql/apollo-client/pull/6448\"\u003e3.0.0\u003c/a\u003e, kicks in and avoids infinite network fetches between the queries.\u003c/p\u003e\n\n\n\n\u003cp class=\"wp-block-paragraph\"\u003ePrior to 4.3, cache feud detection worked by recording the last written query data after a network request. But tool names, descriptions, input names, and input descriptions are model-facing text that can steer an agent toward attacker-chosen arguments, tools, or schema-valid exfiltration. Capture the live tool list, inspect it for hidden or encoded instructions, and compare it with the last approved snapshot whenever the operation or schema source changes.\u003c/p\u003e\n\n\n\n\u003cp class=\"wp-block-paragraph\"\u003e\u003cstrong\u003eIntent flow subversion, bounded but not blocked (\u003c/strong\u003e\u003ca href=\"https://owasp.org/www-project-mcp-top-10/2025/MCP06-2025%E2%80%93Intent-Flow-Subversion\"\u003e\u003cstrong\u003eMCP06)\u003c/strong\u003e\u003c/a\u003e. An injected instruction can\u0026#8217;t conjure capabilities the server never exposed; it can only invoke operations you already approved. That bounds blast radius, but it is not a defense. Steering the agent into a valid, permitted mutation is the attack, not something this constraint stops. The bound widens when execute or ad-hoc mutations are enabled, since \u0026#8220;permitted\u0026#8221; then covers anything that type-checks. Over HTTP with an \u003ccode class=\"\" data-line=\"\"\u003eauth\u003c/code\u003e block, the server is a checkpoint, not an issuer: it validates the caller\u0026#8217;s token against any OAuth-compatible identity provider, per the\u003ca href=\"https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization\"\u003e MCP Authorization spec\u003c/a\u003e, and rejects authorization-server discovery metadata whose issuer differs from that server before trusting its signing keys; \u003ccode class=\"\" data-line=\"\"\u003eissuers\u003c/code\u003e remains operational hardening. What the server does with the validated token afterward is a separate failure mode, covered below.\u003cbr\u003e\u003c/p\u003e\n\n\n\n\u003cp class=\"wp-block-paragraph\"\u003e\u003cstrong\u003eScope creep (MCP02).\u003c/strong\u003e Two checks, two enforcement points: the global \u003ccode class=\"\" data-line=\"\"\u003eauth.scopes \u003c/code\u003elist is validated with the token itself, so it runs on every authenticated request but it is one bar for the whole server, and any token that clears it reaches every tool. Per-operation \u003ca href=\"https://www.apollographql.com/docs/apollo-mcp-server/auth#per-operation-scope-requirements\"\u003erequired_scopes\u003c/a\u003e narrows that: populate it for an operation, and a token scoped to one tool stops working for the rest, rejected at invocation with a 403 \u003ccode class=\"\" data-line=\"\"\u003einsufficient_scope\u003c/code\u003e challenge. The map is opt-in, keyed by operation name, and maintained by hand. Both checks exist only where the \u003ccode class=\"\" data-line=\"\"\u003eauth\u003c/code\u003e checkpoint does.\u003c/p\u003e\n\n\n\n\u003cp class=\"wp-block-paragraph\"\u003e\u003cstrong\u003eAudit and telemetry (MCP08).\u003c/strong\u003e The server logs generously by default: traces, metrics, and logs are tied together by \u003ccode class=\"\" data-line=\"\"\u003etrace_id\u003c/code\u003e, with arguments, query, and response recorded on each span.
